# Roadmap

Kurul is an open-source, self-hosted, Kanban-focused project management tool. The MVP is
complete: Phases 0-9 and the hardening pass that followed shipped as
[`v0.1.0`](CHANGELOG.md#010---2026-08-12), and [`v0.4.0`](CHANGELOG.md#040---2026-08-27) is the
current release, cut on 2026-08-27. The next release is `v0.5.0`. The work ahead is
turning a finished MVP into a launched, trusted product: standing up the demo host the
announcement wave is gated on, and growing the API surface toward a 1.0 compatibility promise.
Work runs on **two parallel tracks**, Hardening and New Features, so stability debt and user
value never queue behind each other.

**Last updated:** 2026-08-27. This file supersedes `docs/roadmap.md` and absorbs the open
items of the 2026-08-13 local audit dashboard (now deleted). Task-level work lives in
[GitHub Issues](https://github.com/dravcore/kurul/issues); release mechanics in
[git-strategy.md](docs/git-strategy.md).

## Next 2 weeks

`v0.4.0` is cut. It carries the two bodies of work that landed on `develop` after the previous
tag: the post-`v0.3.0` audit fix set, tracked in
[Post-launch hardening](#post-launch-hardening), and the eight-phase UI/UX comfort series
([#311](https://github.com/dravcore/kurul/pull/311) through
[#343](https://github.com/dravcore/kurul/pull/343), merged 2026-08-25 to 2026-08-27), tracked in
the [Hardening track](#hardening-track). That leaves the announcement wave as the only P0, and
it waits on one thing, a deployed demo host. Every dependency it has is enumerated once, in the
[Launch checklist](#launch-checklist), and the rows that used to carry a quarter of that list
each now link there.

### Launch checklist

Everything the announcement wave is gated on, ordered, in one place. This list is the single
source: the live-demo row, the launch-window wave row, `OPS-05` and the operator checklist that
used to sit under the deferred table each carried a quarter of it, and now link here instead.

1. **Provision the host and DNS, and name an owner.** One small VPS with `kurul.dev` pointed at
   it. The owner is whoever answers when the demo stops answering; the step is not done until
   that is a name rather than "us".

   to `latest`, and a demo the announcement points at has to be the build the announcement

## API 1.0

**Scope declaration, not a plan. Everything in this section is deliberately unimplemented, and
saying so is the point** — the three rows below are the only API surface 1.0 is expected to
grow, and anything that arrives instead of them should have to argue with this heading first.
Two of the three appear in [Beyond MVP](#beyond-mvp) above as unscheduled items; this section is
where they acquire a shape. Declared sequencing (see Phase 2): **PAT → `/v1` → webhooks**,
decided in [ADR 0031](docs/decisions/0031-api-versioning.md).

What exists today, and is why this can be scoped at all: the API is described by a generated
OpenAPI document, committed at [`apps/api/openapi.json`](apps/api/openapi.json) and served at
`/docs`, with a CI gate that fails when the code and the document disagree
([api-conventions.md](docs/api-conventions.md#the-openapi-document)). A compatibility promise is only
worth making about a contract somebody has written down.

| Item                    | Shape                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/v1` prefix            | A URI prefix on every route, introduced **at** 1.0 and not before — a version segment today would imply a promise this project is not making, during the period the API is most expected to churn ([api-conventions.md](docs/api-conventions.md#versioning)). Introduced by ADR, because the alternative schemes (header negotiation, no versioning at all) deserve to be rejected in writing rather than skipped                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Personal access tokens  | **Shipped 2026-08-23** as the first slice: a second authentication path beside the session cookie, for a caller that is not a browser. Workspace-scoped, revocable, listed by their owner, hashed at rest. Still not promised: OAuth, per-token scopes, and token access to the writes Better Auth performs on a session (session-only until `/v1`, [api-conventions.md](docs/api-conventions.md#authentication))                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Minimal webhooks        | Exactly three events, `task.created`, `task.moved` and `task.completed`, delivered per workspace with an at-least-once signed envelope. Three because they are the events an outside system can act on; the rest of the activity vocabulary is a feed for people. The failure policy (retries, disabling a dead endpoint) is [ADR 0033](docs/decisions/0033-webhook-delivery-and-failure-policy.md), **Proposed**. The open question it turns on is **who owns the endpoint**: the only statement this repository ever carried was that an operator configures the URL, which arrived as prose in a docs pull request rather than as a decision, and the ADR proposes a workspace-owned endpoint instead. Everything else branches off that answer, including whether the work is an M or an L                                                            |
| 1.0 criteria (proposed) | `/v1` is the visible half of 1.0; the promise is the other half, and it has never been written down. Proposed as the whole list, so that it can be argued with before the tag rather than after: (a) the prefix is on every route; (b) `apps/api/openapi.json` is generated, committed, CI-gated, and its `info.version` tracks the package version; (c) every failure is the one error envelope [api-conventions.md](docs/api-conventions.md) documents; (d) pagination, filtering and sorting have the same shape on every collection; (e) a deprecation policy exists in writing, with a minimum notice window; (f) the session-only boundary either disappears or is documented as permanent, so no caller has to discover it; (g) the repo-wide coverage stance is revisited, which [testing.md](docs/testing.md#coverage) already schedules for 1.0 |

Three things this section deliberately does **not** promise:

- **No date, and no ordering between the three** beyond the declared implementation
  sequencing above. They are a scope, not a schedule.
- **No general event stream.** `Activity` has a much larger vocabulary than three types, and
  publishing all of it outward would freeze an internal log as a public contract.
- **No OAuth, no third-party app model, no per-token scopes beyond the workspace.** Each of
  those is a product decision that 1.0 does not need in order to be stable.
